## Open issues

### 1. (P0) Reply-keyboard taps crash the handler — "nothing working"
- **Where:** `lib/Bot.php` `onMessage()`, lines ~127-132.
- **Original:** Menu / Reseller API / Freebies / How to Use reply-keyboard
  buttons answer immediately.
- **Ours:** the lookup map uses **arrays as array keys**:
  `[$this->i->t('btn_menu'), $en->t('btn_menu')] => 'welcome', ...`
  PHP forbids arrays as keys, so evaluating this literal throws
  `TypeError: Illegal offset type`. `webhook.php` catches it, logs it
  and returns 200, so Telegram never retries and the user gets **no
  reply at all**. This is exactly the screenshot evidence: the user's
  `🏠 Menu` and `📖 How to Use` taps (03:24) got zero bot response.
  It also breaks any plain-text message and any state input that
  `handleState()` returns false for (falls through to the map).
- **Fix:** restructure the map as a list of `[labels, action]` pairs.

### 2. (P0) Welcome re-sent as fresh messages on every Menu / /start / unknown text — pile-up
- **Where:** `lib/Bot.php` `sendWelcome()`; called from `cmdStart`,
  reply-keyboard Menu, unknown commands and unknown text.
- **Original:** "Menu re-sends welcome" (analysis doc), but the old
  screen goes away — the user states plainly the chat must not keep
  growing downwards.
- **Ours:** every call sends a **new** animated banner **plus** a new
  `👇 Menu` text message. Tapping Menu three times = three banners +
  three Menu texts below.
- **Fix:** track the current menu message (`menu_msg_id`,
  `menu_media`, `kb_sent`) in `users.state_data` (no schema change;
  `setState()` preserves these keys). `sendWelcome()` edits the
  tracked message's caption in place when it is the banner, deletes it
  and sends a fresh banner when it is a text screen or uneditable, and
  sends the `👇 Menu` reply-keyboard message only once ever.

### 3. (P0) Typed-command screens stack new messages instead of replacing
- **Where:** `showAccount()`, `showPoints()`, `showFreebies()`,
  `showApi()`, `showLanguage()`, `showSupport()`, `showHowTo()`,
  `showOrders()` — all `tg_send` new messages.
- **Original:** screens replace the current screen; the old one goes away.
- **Ours:** `/balance`, `/deposit`, `/orders`, `/freebies`, `/apikey`,
  `/language`, `/support`, `/help` each stack another message below
  the banner.
- **Fix:** new `showTracked($text, $kb)` helper — edit the tracked menu
  message (caption if media, text otherwise); fall back to a fresh
  message + tracking when there is none or the edit fails. All eight
  message-version screens use it.

### 4. (P1) Callback edits ignore API failures — buttons can silently die
- **Where:** the `$edit` closure in `onCallback()` and every caller.
- **Original:** buttons always respond.
- **Ours:** the result of `tg_edit`/`tg_edit_caption` is never
  checked. If the edit fails (message deleted, older than 48h, or the
  `tg_edit_caption` >1024 fallback replaced the message), the button
  appears dead and the tracked message id goes stale.
- **Fix:** result-aware `$edit` closure: success updates tracking
  (including the fallback's new message id); "message is not modified"
  is a no-op; any other failure deletes the stale message and sends a
  fresh one + tracks it. `tg_edit_caption()` marks its fallback result
  with `_fallback_text` so callers track the new message as text.

### 5. (P1) Copy Payment Address and Payment Sent share one callback — copy does nothing
- **Where:** `confirmPurchase()` pay screen and `startDeposit()`:
  both "Copy Payment Address" and "Payment Sent" use `ps:<id>`,
  and `ps` only asks for a TXID.
- **Original:** four distinct buttons — Copy Payment Address/Amount,
  Payment Sent, Check Payment, Cancel Payment.
- **Ours:** tapping "Copy Payment Address" never shows/copies the
  address; it asks for a TXID instead.
- **Fix:** new `copy:<type>:<id>` callback that sends the address as a
  `<code>` message (tappable to copy). `ps` keeps meaning Payment Sent.

### 6. (P1) Payment callbacks mix up orders and deposits — wrong-row updates
- **Where:** `ps` / `pc` / `px` callbacks and `await_txid` state.
- **Original:** n/a (internal).
- **Ours:** the callbacks carry a bare numeric id. `checkPayment()`
  looks only in `orders`; `cancelOrder()` cancels only in `orders`;
  `await_txid` writes TXID only to `orders`. A deposit id that
  collides with an order id can cancel or stamp the **wrong order**,
  and a deposit TXID is never recorded anywhere.
- **Fix:** typed callbacks `ps:o|d:<id>`, `pc:o|d:<id>`,
  `px:o|d:<id>`, `copy:o|d:<id>` and typed state
  `await_txid:o|d:<id>`; each handler reads/writes the right table.

### 7. (P1) Telegram Stars deposit success is never handled — user pays, gets no points
- **Where:** `onSuccessfulPayment()` only handles payloads starting
  with `order:`; `startDeposit()` stars invoices use payload
  `deposit:<id>`.
- **Original:** Stars deposits credit instantly.
- **Ours:** a Stars deposit payment succeeds, Telegram delivers the
  money, the bot ignores it: deposit stays `pending`, no points are
  credited, no message is sent.
- **Fix:** handle `deposit:<id>` payloads — confirm the deposit,
  credit `points`, notify the user. Also guard `onSuccessfulPayment`
  against a deleted product (`$p` null).

### 8. (P1) Points are deducted from the wallet only — wallet can go negative
- **Where:** `createAndDeliverOrder()`: `add_points(-$need,
  'order_payment')` always deducts from `points_wallet`, while the
  affordability check uses wallet + referral combined.
- **Original:** n/a (internal).
- **Ours:** wallet 0 + referral 50, buy for 30 points → wallet becomes
  **-30**.
- **Fix:** deduct wallet first, then referral (`referral_spent`).

### 9. (P1) Points are deducted BEFORE the stock check — failed delivery keeps the points
- **Where:** `createAndDeliverOrder()`: the deduction runs before
  `beginTransaction()`; the stock check that can throw happens
  inside the transaction.
- **Original:** n/a (internal).
- **Ours:** if stock is short the order rolls back but the points
  deduction (already committed) is **not** refunded.
- **Fix:** move the deduction inside the transaction, after the stock
  reservation succeeds.

### 10. (P2) "Add to Favorites" sends a fake confirmation message, no favorites exist
- **Where:** `onCallback()` case `fav`.
- **Original:** product detail has Add to Favorites (backed by a
  favorites list).
- **Ours:** sends a new `❤️ Added to favorites.` message every tap
  (pile-up) and stores nothing; there is no favorites table or list.
- **Fix:** answer the callback with a toast (`answerCallbackQuery`
  text) instead of a message. Full favorites list is a feature gap,
  noted, not built in this fix.

### 11. (P2) "Share" sends a pointless self-message instead of opening the share sheet
- **Where:** `onCallback()` case `share`; `showProduct()` Share button.
- **Original:** Share opens Telegram's share sheet.
- **Ours:** sends `📦 <name> — $x on <bot>!` as a new message to the
  user themselves (pile-up, useless).
- **Fix:** make Share a `btn_url` to `t.me/share/url` with the bot
  link + product text; drop the callback case.

### 12. (P2) Buy Multiple / Custom Amount confirm screens pile up
- **Where:** `handleState()` `await_qty` → `showConfirm($pid, $qty)`
  (no message id → `tg_send`); `await_custom_points` →
  `showDepositMethods($usd)` (`tg_send`); `pp` callback →
  `showDepositMethods()` (`tg_send`).
- **Original:** confirm/deposit screens replace the current screen.
- **Ours:** each step adds another message below the product/points
  screen.
- **Fix:** `showConfirm()` / `showDepositMethods()` accept an optional
  `$edit` callable (callback path passes it); message paths use
  `showTracked()`. `showConfirm` also notifies instead of silently
  returning when the product no longer exists.

### 13. (P2) "View Reviews" shows the user's dashboard, not the product's reviews
- **Where:** `onCallback()` case `rev` → `showReviews()`
  (user's own reviews / pending-to-review list), reached from the

- **Original:** product detail's View Reviews shows that product's

- **Ours:** tapping View Reviews on a product shows "My reviews /

- **Fix:** new `showProductReviews()` (approved reviews for the
  product, Back returns to the product); `rev:<pid>` from product

### 14. (P2) Language change shows a code, not the new language

### 15. (P2) "Message is not modified" can look like a dead button

### 20. (P2) User/product-controlled text is inserted raw into HTML-parsed messages

### 24. (P1) Payment-status lookup did not check order ownership

### 26. (P0) The user's own tap/command messages stack up below — chat keeps growing downwards
- **Where:** `lib/Bot.php` `handle()` / `onMessage()`; `lib/Telegram.php` (no delete helper).
- **Original:** the chat stays clean — a tap or command leaves no trace below; only the bot's single screen message remains (verified from the user's 03:45 screenshots of their own bot vs the original: after every tap the user's `Reseller API`, `/start`, `Menu`, `Freebies`, `How to Use` messages sit stacked at the bottom while the screen edits in place at the top).
- **Ours:** the screen edited in place (fixes 1–3), but every user tap/command message stayed in the chat forever, so the chat still grew downwards with each tap.
- **Fix:** new `tg_delete()` helper (deleteMessage) and, after `onMessage()` has answered, the handler deletes the user's incoming text message (best-effort, failures ignored). Telegram allows bots to delete incoming messages in private chats (Bot API `deleteMessage` docs: "Bots can delete incoming messages in private chats"). Only the user's text messages are deleted; the bot's screen and the one-time reply-keyboard carrier message are untouched. Inline-button taps create no user message, so nothing changes there.

### 27. (P0) Bottom reply-keyboard menu disappears on the user's mobile and never comes back
- **Where:** `lib/Bot.php` `sendWelcome()`; `setState()` preserved keys.
- **Original:** the four-button bottom menu (Menu / Reseller API /
  Freebies / How to Use) is always there.
- **Ours:** the keyboard carrier message ("👇 🏠 Menu") was sent only
  once ever (`kb_sent` flag). Once a mobile client loses the keyboard
  (dismissed, app restart, carrier deleted), the bot never re-sent it,
  so the bottom menu stayed gone on the phone even though it still
  showed in Telegram Web.
- **Fix:** the carrier is now tracked (`kb_msg_id`, `kb_sent_at` in
  `users.state_data`, preserved across state changes) and refreshed by
  `sendWelcome()`: on the first welcome, or when the last carrier is
  older than 15 minutes, the old carrier is deleted and a fresh one is
  sent, so there is still exactly one carrier message and the keyboard
  re-appears on every device. The 15-minute gate keeps rapid Menu taps
  from spamming carriers. Dead `kbSent()` / `markKbSent()` helpers
  removed.

### 28. (P1) No icon animates anywhere — buttons show only static emoji
- **Research (2026-11-06, multiple sources incl. Bot API docs as quoted
  by telegram-bot-ui references and python-telegram-bot docs):**
  animated icons on Telegram bots work two ways — `icon_custom_emoji_id`
  on `KeyboardButton` / `InlineKeyboardButton` (Bot API 9.4, 2026-02-09,
  renders the animated emoji before the button text) and `<tg-emoji
  emoji-id="...">fallback</tg-emoji>` in HTML message text/captions
  (Bot API 6.2). The welcome banner GIF was already animated; the
  buttons/icons were static because none of this was wired in.
- **Eligibility (official rule, the gate that matters):** custom emoji
  can only be used by bots that bought extra usernames on Fragment, or
  in messages the bot sends directly to private/group/supergroup chats
  **if the bot owner has a Telegram Premium subscription**. It depends
  on the OWNER's Premium, not the viewer's. Without that, Telegram
  silently ignores the icons and shows the plain fallback.
- **Status:** plumbing SHIPPED in `lib/Telegram.php` only (optional icon
  param on `btn()` / `btn_kb()` / `btn_url()`, inert when unused).
  The `lib/emoji.php` map/helpers, the `Bot.php` wiring (`abtn()` /
  `akb()`, tg-emoji in texts) and `tools/emoji_tool.php`
  (verify/fetch real ids) are written but HELD BACK uncommitted —
  paused while the behaviour regression in issue 29 is fixed first,
  so no new behaviour ships on top of a broken one. Still needs: (1)
  the bot owner's Premium status confirmed; (2) `php
  tools/emoji_tool.php verify` run on the server to confirm the default
  ids resolve to the expected glyphs; (3) a pack fetch for the remaining
  button icons.

### 29. (P0) REGRESSION — user messages deleted on /start, chat looks wiped; bottom menu still not coming back
- **Where:** `lib/Bot.php` `handle()` (issue 26 delete) and
  `sendWelcome()` (issue 27 refresh skipped by early returns).
- **What the user saw (2026-11-06 ~10:05 PKT):** "/start msg deleted
  and chat deleted", behaviour very bad. Two causes found on review:
  (a) Issue 26 deleted the user's own /start and tap messages after
  answering. Intended to keep the chat clean, but in practice every
  tap made the user's message vanish while the screen often did not
  visibly change, so the chat felt wiped. (b) Issue 27's keyboard
  refresh only ran on the fresh-banner path: `sendWelcome()` returns
  early on a successful edit and on "message is not modified" — the
  normal Menu//start case — so the refresh NEVER ran and the bottom
  menu still did not come back on mobile.
- **Fix:** issue 26 REVERTED — `handle()` no longer deletes the user's
  message at all; the bot behaves like a normal bot (user messages
  stay, screens edit in place). `sendWelcome()` now calls a new
  `refreshReplyKb()` on EVERY path (edit success, not-modified, fresh
  banner), so Menu//start always restores the bottom keyboard when it
  is missing or older than 15 minutes. Nothing else that deletes a
  message was changed.
